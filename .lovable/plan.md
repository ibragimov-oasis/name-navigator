## Где сейчас лежат имена

1. **Статические батчи в репозитории** — `src/data/names/<culture>/batch_XXX.ts` (исламские: 22 батча, остальные по 1). Это «канон», грузится в бандл.
2. **Supabase таблица `names_enriched`** — AI-сгенерированные, подтягиваются в рантайме через `loadEnrichedNames()` в `src/lib/namesStore.ts`.

Проблема: с ростом БД клиент тянет всё больше строк при каждом заходе (limit 1000, потом упрётся), плюс лишняя нагрузка на Supabase.

## Что предлагаю: перенести хранилище имён в репозиторий

**Идея**: БД остаётся только как **буфер для свежесгенерированного** (очередь на ревью). Раз в N минут edge-функция экспортирует «published» строки в JSON-файлы в репо, и приложение читает их статически — без обращения к Supabase для каталога.

### Архитектура

```text
Gemini → names_enriched (status='published')  ← БД-буфер (только новое)
            │
            ▼  (export-names edge function, cron 1×/час)
  public/data/names/<culture>.json   ← статические JSON, кэшируется CDN
  public/data/names/index.json       ← манифест: версия, культуры, счётчики
            │
            ▼
  src/lib/namesStore.ts → fetch('/data/names/index.json') один раз
                          → ленивая загрузка <culture>.json по фильтру
            │
            ▼
  После экспорта: DELETE из names_enriched (или mark exported) — БД остаётся пустой
```

### Конкретные шаги

1. **Edge-функция `export-names`** (`supabase/functions/export-names/index.ts`):
   - Читает все `status='published'` из `names_enriched`.
   - Группирует по `culture`, формирует JSON-файлы.
   - Коммитит их в репо через **GitHub API** (нужен `GITHUB_TOKEN` секрет + repo owner/name) в `public/data/names/<culture>.json` + `index.json` с версией и счётчиками.
   - После успешного коммита: `UPDATE names_enriched SET status='exported'` (или DELETE — обсудим).

2. **Cron**: `pg_cron` зовёт `export-names` раз в час (после нескольких тиков `enrich-names`).

3. **Клиент `src/lib/namesStore.ts`**:
   - Убрать `supabase.from('names_enriched').select(...)`.
   - Грузить `/data/names/index.json` один раз при старте.
   - Ленивая подгрузка `/data/names/<culture>.json` когда пользователь открывает фильтр по этой культуре (или сразу всё — файлы маленькие, JSON 100KB кэшируется CDN).

4. **HTML-страницы** (опция, для SEO): в дополнение к JSON генерировать `public/names/<culture>/<slug>.html` — статические страницы для каждого имени, индексируются Google. Делается тем же экспортёром. Скажите, если нужно — добавлю.

5. **Архив всех имён в репо**: финальный «золотой» датасет периодически собирается в `src/data/names/ai-generated/<culture>/batch_XXX.ts` — это уже попадает в бандл как канон (раз в неделю вручную или авто-PR).

6. **Очистка БД**: после первой выгрузки таблица `names_enriched` остаётся почти пустой (только свежие неэкспортированные). `enrich_runs` чищу старше 7 дней через `pg_cron`.

7. **UI `/admin/enrich`**: добавлю кнопку «Экспортировать сейчас» и счётчик «в очереди на экспорт / экспортировано всего».

### Что нужно от вас

- **GitHub доступ**: для авто-коммита в репо edge-функции нужен `GITHUB_TOKEN` (Personal Access Token с `contents:write` на этот репо) + имя owner/repo. Без него я могу сделать вариант с **скачиванием JSON-дампа** (кнопка в админке → файл → вы вручную коммитите), но это не «автомат».
- **HTML-страницы** для каждого имени (для SEO) — делать или хватит JSON?
- **Удалять** из `names_enriched` после экспорта или **помечать** `status='exported'` (нужно для дедупликации, чтобы Gemini не сгенерил то же имя заново)? Рекомендую **помечать** — только id + name остаются, это копейки по объёму.
